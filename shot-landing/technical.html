The Tech of

A look under the hood at how KillerShot keeps every capture in an encrypted album, freezes the desktop, captures covered windows, keeps every pixel, and records the screen.

Tech stack

KillerShot needs Windows 11 (build 22000 or later) on x64. Window capture uses the Windows Graphics Capture API, and the minimum keeps that one path for every user instead of a fallback that cannot see covered windows.

The encrypted album

The album is one SQLCipher database, Library.kshot in %LOCALAPPDATA%\KillerShot. Its pictures, thumbnails, window titles, notes, recognized text, QR results and search index are stored in encrypted database pages. Reading that content requires the key; the file's salt is stored unencrypted so SQLCipher can derive the key from a password.

The key. By default the album uses a random 256-bit key from the system's cryptographic random number generator. KillerShot hands it to SQLCipher in raw-key form and protects it with Windows DPAPI in Library.key, scoped to the current Windows user with app-specific entropy. This lets KillerShot open it without a prompt under that account. It does not protect an open album from software running as that user.

A password. Setting a password rewrites the album under the password and deletes Library.key, so only the password opens it. SQLCipher stretches the password with PBKDF2-HMAC-SHA512 over 256,000 rounds, with a random salt kept at the start of the file. Removing the password rewrites the album again under a fresh random key sealed to your account. A forgotten password cannot be recovered, and the password check compares in constant time.

The cipher. SQLCipher encrypts each 4 KB page with AES-256 in CBC mode under its own random IV and signs it with HMAC-SHA512, so a changed or damaged page is refused instead of being read as garbage. The native library is built from the upstream SQLCipher 4.18.0 source with LibTomCrypt, embedded in KillerShot.exe and code signed.

Rekeying. A password change uses sqlcipher_export to write a new encrypted database under the new key. KillerShot closes the connections and clears the pool before replacing the old file, then updates or removes Library.key and reopens the album. This avoids changing the active database in place with PRAGMA rekey.

The capture pipeline

1. Freeze. When a shortcut fires, KillerShot hides its own editor if it is open, waits for the desktop to repaint without it, and copies the whole virtual desktop in one pass. The list of monitors and the visible windows, topmost first, are recorded at the same moment.

2. Choose. Region mode shows that copy on every monitor, one image pixel per device pixel, so the selector itself can never appear in the result and a menu that closes when you click stays in the picture. Monitor and all-monitor modes crop straight from the copy without showing anything.

3. Window. Window mode asks Windows Graphics Capture for one frame of the window, which includes the parts other windows cover. The rounded corners Windows 11 draws are filled from the frozen desktop behind them, so the picture has no transparent or black corners.

4. Output. The finished bitmap goes to the clipboard, the capture library and the output folder, according to your settings. A cancelled capture produces nothing and leaves the clipboard and the last mode as they were.

Rendering

The About card (F12) has a rendering choice: Automatic, Hardware or Software. Automatic uses software rendering during Remote Desktop and remote-control sessions, where hardware rendering can show a black window. The choice applies the next time the window opens.

What is not captured

Content an app marks as protected, such as some streaming video, comes out black; Windows withholds it from every screen capture. A minimized window cannot be captured in window mode. A desktop capture of an HDR monitor is converted to standard range by Windows and can look washed out.

The data model

The album stores capture data, collections, QR results, search data and schema metadata inside the encrypted database. Times are stored in UTC and shown in local time.

TableWhat it holds
capturesOne row per capture: when it was taken, its width and height in pixels, the capture mode, the window title and program it came from, its collection, a note, the text Windows read from it, a JPEG thumbnail no larger than 512 pixels on its long side, and the full picture as a lossless PNG
collectionsEach collection's name and when it was made. Deleting a collection keeps its captures and leaves them in no collection
capture_qrDecoded QR results for each capture, including their text and positions in the picture
capture_searchAn FTS5 full-text index with one row per capture, keyed by the capture's id: the window title, the program, the note, the text read from the picture and the collection name
metaKey and value pairs, holding the schema version

One shared connection serves the app, with database operations guarded by a lock. Capture changes update the search index, and history pruning removes associated search and QR rows. Card and collection colors are display settings and live in settings.json, outside the encrypted album.

Search and the text in pictures

After a capture is stored, Windows OCR (Windows.Media.Ocr) reads its text in the background, newest first, in the languages of your Windows profile. Nothing leaves the PC. That text, the window title, the program name, the note and the collection name go into an FTS5 full-text index that ignores accents, and each word you type matches as the start of a word.

A capture taken while a password-protected album is locked waits in memory and is stored when you unlock it. The history limit keeps everything, or only the last 100 to 5,000 captures or 30 to 365 days. Windows' Screenshots folder is read from disk and watched for new files; its pictures enter the database only when you add them.

Pixels, DPI and scaling

KillerShot runs per-monitor DPI aware (PerMonitorV2), so every coordinate it handles is a physical screen pixel. A selection that crosses a 100% monitor and a 150% monitor is still a plain rectangle of real pixels.

Every capture is stored as a 96 DPI bitmap, so WPF never rescales it for the monitor it is shown on, and the file you save has exactly the pixels you selected. An image you open from disk is copied into a 96 DPI bitmap for the same reason.

Clipboard and files

A capture is put on the clipboard twice in one data object: as PNG, which keeps every pixel for apps that read it, and as a standard bitmap for everything else. The data stays available after KillerShot exits. A clipboard held by another program is retried briefly, then reported.

WhatWhere
Settings%APPDATA%\KillerShot\settings.json
Capture library%LOCALAPPDATA%\KillerShot\Library.kshot, every capture as PNG with a thumbnail, in one SQLCipher database (AES-256). The key is a random 256-bit key sealed with Windows DPAPI to your account in Library.key, or your password

Saved files are written to a temporary name and then moved into place, so a failed write never leaves a cut-off image behind.

The recording pipeline

A capture thread reads the recorded rectangle on a steady clock through Windows Graphics Capture, with one capture session for each monitor the rectangle covers, and hands each frame to an encoder thread. Only the recorded part of each monitor is copied off the graphics card, so recording every monitor keeps the frame rate you set. When the encoder falls behind, frames are dropped rather than letting the clock drift, and paused time is cut out of the timestamps.

MP4 frames go to the H.264 encoder built into Windows. The video size is rounded down to even numbers, which H.264 needs. Sound is captured on its own clock and filled with silence when nothing is playing, so sound and picture stay in step.

Large MP4 recordings. The H.264 encoder in Windows accepts frames up to 4096 x 2304 pixels: 36,864 blocks of 16 x 16 pixels with no side over 4096, the frame size limit of H.264 level 5.1. One 4K monitor fits. A larger area is scaled down to fit before it reaches the encoder, keeping its shape, so three 1920 pixel screens side by side at 5760 x 1080 come out at 4096 x 768. GIF recordings keep the full size.

GIF frames are reduced to a palette per frame and only the area that changed since the last frame is stored. That keeps a recording of a mostly still screen small.

Command line and KillerMCP

The command line is compiled into KillerShot.exe and runs behind its --cli switch, in its own process, without the tray, the shortcuts or the single-instance claim. It uses the same capture, recording and file code as the window. See the command reference.

KillerMCP runs those commands for AI agents and passes back the JSON they print. It never asks for overwrite and leaves the clipboard alone unless asked. See the KillerMCP page.

Privacy & footprint

KillerShot has no account and no analytics. Its one network request is the update check: on startup unless you turn it off on the About card (F12), and whenever you open About, it asks GitHub for the latest release. Installing an update is always your choice, and the release notes link opens the GitHub releases page in your browser.

Encryption protects the album at rest, including its image data, metadata and search index. PNG and JPEG exports and MP4 and GIF recordings are ordinary files outside it. The live Windows Screenshots collection reads existing files without encrypting them; adding one to the album does not encrypt or remove the original. Clipboard copies follow Windows clipboard history and sync settings, which can send a copy to other devices if enabled.

To redact before anything leaves KillerShot, turn on Review before copying or saving in capture settings. Each capture then waits in the editor, and nothing reaches the clipboard, a file, another program or email until you choose Copy and save. The album still keeps the encrypted original, and anything copied or saved from the album is the edited result.
